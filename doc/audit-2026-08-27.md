## 4. Analyse racine P1 (mécanisme run_dir)

`run_state.py` (`weekly-telemetry-aggregator/run_state.py`) :

- `activate_run(output_dir, date, run_time)` (L49-77) crée **toujours** un run dir neuf
  `runs/<date>-<uuid8>` et écrit `run_state.json["run_dir"]` + le symlink `runs/current`.
- `resolve_active_run_dir(output_dir, date)` (L80-94) lit `run_state.json["run_dir"]` ;
  si aucun run actif → fallback legacy = `output_dir` (racine).
- Grep `main.py` : **seul `run()` (L649) appelle `activate_run`** ; `harness()` (L1159),
  `releases`, `report`, `insights`, `watch_distill`, `harness_remediation` utilisent
  `resolve_active_run_dir`.

Donc `weekly_run` est le seul créateur de run dir ; `releases`/`harness` ne font que
résoudre le run actif. En fan-out **parallèle**, si `releases`/`harness` résolvent
`run_state.json` **avant** que `weekly_run` n'ait activé le dir, ils tombent sur le run dir
stale (ou legacy) ≠ celui de `weekly_run` → fragmentation.

**Correctif** : sérialiser `weekly_run` (T) **avant** le fan-out de `releases`+`harness`
(V+H). Chaque run garde son propre UUID (garantie F1 « jamais de collision » préservée),
mais V+H partagent le dir de T car ils résolvent après activation. Aucun changement moteur
requis (le test `test_rerun_same_anchor_creates_fresh_run_dir` reste valide).
